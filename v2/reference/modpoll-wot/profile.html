Executable profile 0.2¶

The published Modpoll 2.0.0a2 preview uses modpoll-wot==0.2.0a1. Shared interpreter 0.2.0a3 and current development source execute only profile 0.2; profile 0.1 must be migrated before use. Older immutable application and interpreter releases keep their original behavior. Package, profile and metadata schema versions are independent; no local-path dependency is introduced.

Source and instances¶

Product TM is the maintained source; TD is a generated instance artifact and a supported input. A single --config accepts either format based on content, independently of filename/URL. Invalid input fails its selected schema without retrying another kind. Fixed vocabulary aliases are required.

Property DataSchemas hold standard types, access flags, units and constraints. Forms supply literal PDU addresses, quantities, raw modv:type, entities and byte/word order. Quantity defaults to 1; byte/word order flags default to true. DataSchema integer does not imply a particular raw width. A combined read/write Form or disjoint operation-specific Forms are accepted when they describe the same mapping. Duplicate operations or disagreeing mappings fail.

Acquisition only holds explicit physical blocks and property names:

{
  "modv:entity": "HoldingRegister",
  "modv:address": 40000,
  "modv:quantity": 8,
  "modpoll:members": ["counter", "signed", "measurement"]
}

This group object is a project extension, even though its fields reuse Modbus vocabulary. Group order, holes and boundaries are preserved without coalescing or splitting. Every property belongs to one group; explicit aliases may share addresses. Decoder metadata and offsets are derived from Forms. Offsets count words for register tables and physical bits for bit tables. Mixed byte orders are per member.

TM Forms can omit href. Standard TM placeholders are also supported. CLI binds host/port/Unit ID; TCP port defaults to 502 and Unit ID to 1 (range 1–254). Reserved placeholder names are HOST, PORT, UNIT_ID and AUTHORITY (host plus port, including IPv6 brackets). Named instance flags take precedence over --param values for reserved bindings. Other parameters use --param NAME=JSON. A whole value placeholder preserves its JSON type. Missing, malformed or unused bindings fail; arbitrary JSON patches and code execution are not supported.

TD declarations are validated before overrides. Standard Form modv:unitID, when present, must agree with the URI and all other Forms and is updated on explicit rebinding. Source TM identity is copied as defined by TM derivation; use an id placeholder and a persistent instance UUID parameter for multiple devices. The platform owns instance identity; the interpreter does not infer a physical identity from IP/port or silently create a random ID. Without explicit flags its endpoint and Unit ID are authoritative. Explicit overrides update all Forms in the effective TD and cannot hide inconsistent source metadata. Listening wildcard addresses cannot be exported. Plain IPv6 literals are canonicalized; scoped IPv6 addresses are currently rejected. Simulators must distinguish listening interfaces from advertised endpoints. Unbound TM execution supports explicit serial/UDP connections; concrete TCP TD export requires a TCP endpoint and never invents RTU/UDP URLs. A bound TCP instance cannot silently become serial/UDP.

Necessary extensions¶

Form field

Meaning

modpoll:multiplier

Finite number/decimal string; engineering = raw × multiplier, including zero/negative values

modpoll:bit

Bit 0–15 of raw xsd:unsignedShort; boolean property

modpoll:codec

float16 or historical register bool/bool8/bool16 array codec, with raw xsd:hexBinary

modpoll:byteLength

Exact UTF-8 capacity when different from the full register span; bytes, not characters

modpoll:bitPacking

legacy-msb for deliberately packed numeric/string bit-table payloads

Native Coil/DiscreteInput booleans/boolean arrays use xsd:boolean and physical counts without an extension. Register boolean scalars use xsd:boolean, quantity 1. Register strings apply byte/word order to the padded register span before taking the declared byte capacity. Legacy register boolean arrays retain their historical byte interpretation and widths. Explicit packed bit codecs retain legacy behavior, including ignoring word order; they are not portable scalar Modbus mappings.

Property schemas are retained in immutable Model.properties_json for consumers. This does not invent manufacturer ranges, generate simulator state, enforce business ranges on live samples or add inverse engineering-value writes. No scheduler, cache or waveform is implied. Unsupported pollingTime/timeout execution, inheritance, optional members, imports, root operations and non-nosec security fail explicitly. These are defined subset limits, not silent fallback behavior.

API and CLI¶

from modpoll_wot import load_model, instantiate, export_td
model = load_model("meter.tm.json", host="127.0.0.1", port=5020, unit_id=7)
model, effective = instantiate(document, host="127.0.0.1", unit_id=7)
td = export_td(document, host="127.0.0.1", target="project")

No input is mutated, no connection opened, and execution needs no temporary TD. Without an endpoint instantiate's second result is a partial description; only export_td promises a complete TD. Exports pass bundled TD 1.1, the pinned official Modbus schema and project cross-field checks offline. See schemas/SOURCES.md.

From a checkout of this repository (use modpoll-wot directly with an installed wheel):

uv run modpoll-wot export tests/fixtures/modsim.tm.json --host 127.0.0.1 \
  --port 5020 --unit-id 7 -o /tmp/modsim-instance.td.json
uv run modpoll-wot validate /tmp/modsim-instance.td.json --profile

Existing output files are never overwritten. These subcommands require shared package 0.2.0a2 or newer. The shared package supplies models/metadata, not a Modbus client/server, scheduler or MQTT service.

Shared TD and binary media parameters¶

Project TDs may retain acquisition metadata when consumed by third-party tools. node-wot 0.9.2 preserves unknown project fields without executing them; removing those fields is not a prerequisite for consumption. Prefer one generated TD per TM, shared by project tools and external Consumers.

Native scalar Forms may specify octet-stream length, signed and byteSeq parameters. The interpreter checks them against the raw type, quantity and byte/word order and rejects conflicts, duplicates and unknown parameters. Parameterized custom codecs, arrays and transformed values are not supported. The ADAM examples in modsim use this shared representation; filenames mark outputs as *.generated.td.json and only TMs are maintained by hand.

Actual external Consumer¶

The node-wot-0.9.2 export target is verified with pinned @node-wot/core and @node-wot/binding-modbus 0.9.2. It emits standard TD Forms, removes acquisition metadata and supplies octet-stream length/signed/byteSeq media parameters. The external Consumer contains no project decoding or value conversion. Separate operation Forms use FC16 for register writes, avoiding the client's FC6 byte swapping. Word order has no effect on a single register.

Supported targets include 16/32-bit integers, 32/64-bit floats and scalar booleans. Four read byte/word orders are verified. Multiword mixed-order writes are rejected because this client cannot encode them correctly. Strings, arrays, 64-bit integers, custom codecs, bit extraction and multipliers fail by property name rather than being stripped or misrepresented. Project TD output retains those semantics. No HTTP/cache endpoint is declared without an actual service.

CI in this repository tests the source on the supported Python range, builds the wheel and sdist, checks the installed wheel from outside the source tree, and runs the Modpoll and Modsim test suites against the built wheel. The node-wot interoperability gate remains in Modpoll and runs against its pinned release.

Promotion order¶

The canonical tests/fixtures/modsim.tm.json is the four-block/37-property source; generated TDs are artifacts. Tests cover value/request equivalence, mixed orders, aliases, holes, UTF-8 byte capacities, physical bit offsets, parameters and external read/write round trips.

Pass source and installed-wheel checks, publish the immutable shared package via this repository's release workflow, verify registry installation, then independently update consumer exact pins and CI. Project versions need not match. Until producer-first publication completes, no consumer requires an unpublished version or local path. The modsim TD runtime and platform lifecycle remain separate implementation tasks; this contract does not claim those applications are implemented.

Point tables¶

project_point_table(tm_bytes) produces rows in acquisition member order. Addresses are zero-based and quantities count the registers or bits read by the individual Form. Read function codes are null for write-only points. A writable flag records access without inferring a write function code. Multipliers are decimal strings when present. Each readable row carries its point fingerprint; write-only rows carry null.

Point and model fingerprints¶

A point fingerprint identifies how one readable property is acquired and decoded, independently of the file that contains it. A model fingerprint identifies the set of readable point mappings of a whole model. Verification statistics are keyed by the model fingerprint: titles, descriptions, units, property names and member order do not change it, so a custom TM whose read mappings are unchanged shares the fingerprint and statistics of its upstream TM, while any change to a read mapping, or adding or removing a readable point, starts a new one.

point_fingerprints(model) accepts a TM or TD, as a parsed document or exact bytes, and returns {property: fingerprint} for every readable property. model_fingerprint(model) returns the model fingerprint. modpoll-wot fingerprint FILE prints both as JSON ({"model": ..., "points": {...}}). The model is instantiated without instance arguments, then each property's read Form is reduced to this canonical object:

Key

Value

type

Property DataSchema type

modv:entity, modv:address, modv:quantity, modv:type

From the Form; quantity is filled with its default

modv:mostSignificantByte, modv:mostSignificantWord

From the Form, defaulting to true

modpoll:codec, modpoll:bit, modpoll:bitPacking

Only when present

modpoll:multiplier

Only when present, as a plain decimal string without exponent or trailing zeros (0.1, 100)

modpoll:byteLength

Always for xsd:string, filled with the full span capacity by default; never otherwise

The fingerprint is pf1: followed by the lowercase SHA-256 hex digest of the object serialized as UTF-8 JSON with sorted keys, no whitespace and non-ASCII characters unescaped. Property names, titles, descriptions, units, ranges, write Forms, endpoints and Unit IDs do not contribute. Flags that a type cannot use, such as word order for a single register, are kept as written: equivalent spellings may split statistics but never merge different mappings. The model fingerprint is mf1: followed by the SHA-256 hex digest of the sorted, deduplicated point fingerprints serialized as a JSON array without whitespace. Aliases with identical mappings count once; write-only properties do not contribute. tests/fixtures/modsim.fingerprints.json pins the canonical strings, point fingerprints and model fingerprint of the 37-property fixture for other implementations. Changing either canonical form requires a new prefix. tests/fixtures/conformance.fingerprints.json does the same for conformance.tm.json, which covers every byte and word order and each Form extension; with conformance.data.json it is also what the workspace integration tests serve with modsim and read with modpoll.

Rejection vectors¶

An implementation that accepts or stores Thing Models without this package, such as a web service, must refuse what this loader refuses. tests/fixtures/conformance.rejections.json, next to the fingerprint vectors, lists documents that must be refused: each vector is a JSON Patch (RFC 6902, add, replace and remove only) applied to conformance.tm.json, with the name of the rule that refuses the result. The unchanged model must be accepted. The rule names group the vectors for readers and are not an error code contract; schema marks a vector that one of the bundled JSON Schemas already refuses. Two differences cannot be expressed as vectors, because they disappear when JSON is parsed outside Python: duplicate object keys, and an integer written as a float such as 1.0.

Verification reports¶

A verification report records one reading of a Thing Model on a physical device. Its schema is schemas/verification-report-5.json (JSON Schema 2020-12; schemas 3 and 4 remain valid). A report carries:

  • Optional product: the catalog product ID <manufacturer>/<model-number>. The receiving service resolves the product from the model fingerprint, so tools do not need to know it; older reports may still carry it. A fingerprint that matches no known product is rejected.

  • model: the SHA-256 of the exact TM bytes, its model fingerprint and its source. Catalog models add the 40-character catalog commit as ref; the product ID and commit identify the package's model.tm.json. Custom TMs add an opaque version reference. Local models add no ref.

  • tool: the reporting tool's name and version, and the modpoll-wot version.

  • transport (tcp or rtu) and the reading date.

  • Optional environment: chassis product ID, firmware and a short configuration note, such as an input range code.

  • points: per property, its fingerprint, the read result (ok, exception with its exception code, no-response or not-tested) and the user's judgment of the value (confirmed, rejected or unchecked). Only a successful read can be judged.

  • identity on an identity point (schema 5): match or mismatch, see below.

Identity points¶

An identity point is a readable property whose DataSchema declares const: the value the document gives for this product, such as a meter code or a module name. identity_constants(model) lists them. A tool compares the value it reads with the constant on the local computer and reports only the result, so the value itself still never leaves the computer. identity_result(const, value) applies JSON Schema const equality: numbers compare by value (137 equals 137.0), booleans never equal numbers, and strings compare exactly, so a value with a multiplier or a float raw type should not be an identity point. In a schema 5 report every successfully read identity point carries identity, and no other point does; a failed read carries none. A report with a mismatch was read on different hardware, so receiving services do not count it. const does not contribute to point or model fingerprints: marking an identity point later keeps every fingerprint and every earlier report valid.

A report is a full read when its points cover every readable property of the model and every read is ok, so that executing the whole modpoll:acquisition plan raised no error. Receiving services derive this from the stored per-point results.

The schema rejects every other field. Endpoints, Unit IDs, serial numbers and read values therefore cannot be sent. Configuration notes are free text, so the reporting tool shows the report for review before upload. Review markers and account data belong to the receiving service, not the report.

validate_report(report, model=tm_bytes) and modpoll-wot validate-report REPORT [--model TM] check the schema and unique properties. With the model, they also check its hash and model fingerprint, and that every point names a readable property with a matching fingerprint, and for schema 5 that identity appears exactly on the successfully read identity points.

Tool sessions and Workspace references¶

A tool such as modpoll or modsim signs in to ModioHub with the browser authorization flow (OAuth 2.0 device authorization grant) and receives a tool session token that lives 7 days. This package only defines where the token is kept and how a Workspace Thing Model is named, so that a login made by any tool works for every tool on the same computer. It makes no request.

  • Token: MODIOHUB_TOKEN in the environment wins; otherwise the credentials file. MODIOHUB_URL names another server (an origin, https unless local; default https://modiohub.com).

  • File: MODIOHUB_CREDENTIALS, else modiohub/credentials.json under $XDG_CONFIG_HOME (default ~/.config) or %APPDATA%. Mode 0600 in a 0700 directory; a file other users can read is refused. Content: {"version": 1, "servers": {"<origin>": {"token", "expiresAt", "githubUser"}}}. Each server keeps its own login; an expired token is ignored.

  • Reference: modiohub:<id>@<version> names a version of a custom Thing Model. The id is the 16 characters of the custom Thing Model, the version a number or latest (the default). Shared versions can be read without a login.

load_session, save_session, forget_session, server_url and parse_reference implement this.

Simulation data¶

Simulation data describes the values a simulator serves for one device of a Thing Model. Its schema is schemas/simulation-data-1.json (JSON Schema 2020-12), and Modsim loads it with --data.

Field

Meaning

version

"1", required

initial

Property name to static value; the default way to give a value

generators

Property name to a changing value: constant (value), sine (center, amplitude, positive period), ramp (start, rate, minimum, maximum) or noise (minimum, maximum)

bindings

Target property name to the source property it follows

tick

Update interval in seconds, at least 0.001, default 1

seed

Random seed, default 0

writePolicy

hold (default) or overwrite: whether a generator overwrites client writes

Values are engineering values as Modpoll reads them. Every other field is rejected, so simulation data never carries executable code; simulator behavior scripts are configured in the simulator itself. Simulation data is not a Modbus data table (modv:entity).

A Modpoll --export snapshot is accepted as simulation data. A document without version is a snapshot, mapping device titles to point values; the version key alone decides the shape. load_simulation_data(document, title=..., properties=...) takes the device entry whose title matches, or the only entry, and returns its values as initial. Points Modpoll could not read (null) are left out and listed in unread. A timestamp entry is a point only when the model has a property of that name. With properties, every referenced name must be a property of the model. Snapshots are instance data: they stay on the user's computer and are never part of a catalog, Thing Model or verification report.

scaled_raw(value, multiplier) returns the raw integer behind a scaled value. It accepts the raw integer times the multiplier as an exact decimal (230.1 with 0.1) or exactly the float Modpoll computes, float(raw) * float(multiplier) (230.10000000000002 with 0.1), and rejects everything else without a tolerance threshold, so any value Modpoll exports can be served again unchanged.

modpoll-wot validate DATA --kind data checks a data document or snapshot.
